# 文件夹树技术评估 —— npp-explorer-plugin 是否值得复刻

> 评估基线：本仓库 `dec7c62`（v1.0.8）+ 本地半成品治理改动。
> 被评估对象：`/media/wtian/GithubProjects/npp-explorer-plugin`（Notepad++ Explorer 插件，GPL-2.0 项目，部分文件 MIT）。
> 判据：**极致高性能**（打开文件夹不能有 O(N) 全量 IO / O(N) 内存 / 主线程阻塞；大目录不能有静默数据不一致）。
> 结论：**不满足，不复刻，按需求方「宁可不做也不将就」的约束，本轮不实现该功能。**

## 1. 评估范围

只读审计该插件与目录树性能直接相关的实现：

`DirectoryReader.*`、`WorkerThread.*`、`ExplorerTasks.*`、`FileSystemService.*`、`FileSystemWatcher.*`、
`ExplorerModel.*`、`ExplorerViewModel.cpp`、`TreeModelSynchronizer.cpp`、`TreeView.cpp`、
`FileList.cpp`、`QuickOpenDialog.cpp`、`ExplorerDialog.cpp`、`Explorer.cpp`。

同时统计本仓库规模作为量级参照：约 **3388 个文件**（`scintilla` 266、`lexilla` 980、`npp-linux/src` 48、`PowerEditor` 60，其余为构建产物/资源）。真实 monorepo 常见十万级文件，比这高两个数量级。

## 2. 项目性质（决定了「复刻」是否成立）

这是 **Windows 版 Notepad++ 的 Win32 插件**，不是跨平台库：

- UI 基于 `HTREEITEM` / `HWND` / `commctrl.h` TreeView-ListView，依赖 `NppPlugin/DockingFeature` 的 docking API；
- 文件系统用 `FindFirstFileW` / `SHFileOperationW` / `SHGetFileInfo` / `ReadDirectoryChangesW` / COM(`CoInitializeEx`)；
- 项目文件是 `Explorer.sln` / `.vcxproj`，源码里直接 `#include <windows.h>`。

**可移植代码行数 = 0。** 所谓「复刻核心代码」实际等于按它的架构用 Qt 重写一遍，而不是搬代码。

## 3. 值得肯定的高性能设计（树视图本身）

| 设计 | 证据 |
|---|---|
| 惰性单层加载 | `ExplorerDialog.cpp:337-348`：`TVN_ITEMEXPANDING` 才 `FetchChildren(hItem)`；`FileSystemService.cpp:151-190` 的 `GetDirectoryEntries` 只 `FindFirstFile`/`FindNextFile` 当前一层，不递归 |
| IO 不占 UI 线程 | `ExplorerTasks.cpp:53-75` 在 `WorkerThread` 执行，`ExplorerViewModel.cpp:358-365` 经 dispatcher `Post` 回 UI 线程再 `OnCompleted()` |
| 增量更新而非重建树 | `TreeModelSynchronizer.cpp:57-188`：有序 diff-and-patch，插入/删除/原地更新，保留已加载子树 |
| 有子节点判定提前退出 | `FileSystemService.cpp:115-149`：`HaveChildren` 找到第一个符合项立即 `break` |
| 防任务堆积 / 防过期回写 | `WorkerThread.cpp:64-83` 按 category 清理队列；`ExplorerTasks.cpp:97-125` 图标任务用 `cancelToken` + `generation`；`FileList.cpp:278` 校验 generation |
| 优先级队列 | `WorkerThread.cpp:52-62,102-108`：高/低优先级双队列 |

Quick Open 的全量扫描**只在用户主动按 Ctrl+P 时触发**（`Explorer.cpp:390-408`），不是打开文件夹的常规路径。这一点必须公平记录。

## 4. 不满足「极致高性能」的证据

1. **全量递归预扫描 + O(N) 常驻内存**（Quick Open）
   `QuickOpenDialog.cpp:597-632` → `DirectoryReader.cpp:94-130`：`ReadDirRecursive` 用 `std::filesystem::directory_iterator` 递归整棵树，每个文件一次回调；
   `QuickOpenDialog.cpp:616-627` 为每个文件 `AddEntry`（堆分配 `QuickOpenEntry`）。切换工作区或按 Ctrl+P 即 O(N) 磁盘 IO + O(N) 内存。
   本仓库 3388 文件尚可控，十万级仓库是秒级 IO 与百 MB 级常驻内存。

2. **每次按键 O(N) 重新评分**
   `QuickOpenDialog.cpp:421-493`：查询变化时 `GetUnscoredEntries()` 遍历全部条目，每个条目最多两次 `FuzzyMatcher::ScoreMatch`（文件名 + 相对路径）；退格/换前缀走 `ResetScore` 全量重置（`:447-454`）。

3. **单工作线程串行，无法抢占**
   `WorkerThread.cpp:85-118`：目录读取、树图标、文件列表图标共用一个线程。优先级队列只能影响「尚未取出」的任务；正在执行的低优先级 `TaskFetchIcons`（`ExplorerTasks.cpp:100-120`，逐文件 `SHGetFileInfo` + COM）会阻塞后续高优先级目录任务。

4. **跨线程标志非原子（UB）**
   `DirectoryReader.h:43-44` 的 `_needsStop` / `_reading`、`FileSystemWatcher.h:50` 的 `m_stop`、`WorkerThread.h:76` 的 `_running` 都是普通 `bool`，在 `-O2/-O3` 下无内存屏障，存在数据竞争，可能丢失停止信号或死循环。

5. **递归 watcher 会静默丢事件**
   `FileSystemWatcher.cpp:79-120`：`ReadDirectoryChangesW(..., bWatchSubtree=TRUE)` 只申请 16KB 缓冲，且只监听 `FILE_NAME | DIR_NAME | CREATION`（漏 `LAST_WRITE`/`SIZE`/`ATTRIBUTES`）；
   `:152-155` 在 `retsize == 0`（缓冲溢出）时直接 `continue`，**丢弃该批全部变更**。大目录批量操作后树与磁盘会不一致。回调还在工作线程直接调用（`:161-181`），未见统一 marshal 到 UI 线程。

6. **图标逐项 shell 查询、无持久缓存**
   `ExplorerTasks.cpp:100-120` 对每个条目单独 `FetchIcons`；`FileList.cpp:606-610` 只有 `cancelToken`/generation 防过期，`ExplorerModel.h:47-49` 的 view cache 随刷新重置，没有跨目录的图标缓存。

7. **diff 内存在线性查找**
   `TreeModelSynchronizer.cpp:137-139`：diff 循环里 `dialog.FindFolderAfter(...)` 线性搜索；排序比较器 `:89-98` 每两元素调用一次 `CompareStringEx`（Win32 locale API）。大目录下有 O(N²) 风险。

8. **平台不可移植**（见 §2）：上述所有机制都要在 Qt/Linux 上重写，重写过程中还会把 1–7 的取舍一并带进来。

## 5. 结论

该插件的**树核心架构**（惰性单层 + 后台 IO + 增量 diff + 任务取消）是合理且高性能的；但作为整体：

- 它附带一套 O(N) 全量扫描 / O(N) 内存的 Quick Open 索引，以及 O(N) per keystroke 的匹配；
- 单线程串行 + 非原子停止标志 + 会丢事件的递归 watcher；
- 且是 Win32 专用实现，无法直接复刻。

对于「打开文件夹 → 左侧目录树 → 点击文件打开」这个需求，**引入它等于引入降级**：Qt 原生 `QFileSystemModel` 已经内建惰性加载（`canFetchMore`/`fetchMore`）、inotify watcher、图标缓存与排序，根本不需要自建线程、同步器或全量索引。

按需求方明确的「不满足高性能要求，宁可不做也不能将就」，本轮：

- **不复刻该插件代码**；
- **不实现「打开文件夹」功能**；
- 不写 `docs/开发计划2.md` 的新增开发计划（无开发任务）。

## 6. 若后续决定实现，唯一建议路径

Qt 原生，零全量扫描：

| 环节 | 方案 | 复杂度 |
|---|---|---|
| 目录数据 | `QFileSystemModel` + `setRootPath` / `setRootIndex`，`setNameFilters` 只做视图过滤 | 打开文件夹 O(根层条目数)，无预扫描 |
| 视图 | `QTreeView`（隐藏 size/type/date 列），`setSortingEnabled` | 惰性，自带 watcher 与图标缓存 |
| 布局 | `QDockWidget(Qt::LeftDockWidgetArea)` 或在 central 用 `QSplitter` 左树右 `TabManager` | 需处理无边框自绘标题栏 + `setMenuWidget` 的既有布局 |
| 打开文件 | `clicked` → `model->filePath(index)` → 复用 `MainWindow::openFile()` | 与现有会话/编码/监控链路一致 |
| 入口 | 文件菜单 + 工具栏动作，`QFileDialog::getExistingDirectory` | 与现有 `ShortcutManager` 自动收集兼容 |

该路径下需要按用户规则先写 `docs/开发计划2.md`、按 TDD 先写红灯测试（含大目录惰性加载验证），再实现。
