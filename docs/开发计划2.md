## 2. 设计原则

1. **TDD**：每模块先写测试并跑出红灯，再写实现跑到绿灯；绿灯前不进入下一模块。
2. **不静默**：任何降级都必须有一条用户可见、带原因与后果的提示，以及一条可断言的程序状态。
3. **不丢数据**：保存失败绝不 `SETSAVEPOINT`、绝不清脏标记、绝不留下半成品文件（事务写）。
4. **单一事实来源**：快捷键表从真实 `QAction` 收集，自动包含 v1.0.8 的「代码格式化」，不再维护第二份清单。
5. **可测性优先**：序列化、路径探测、冲突检测等纯逻辑从 QWidget 抽出，测试同时打纯逻辑与 offscreen UI 绑定。
6. **不回退 v1.0.8 功能**：所有改造都要在测试中验证格式化、拖放、图标相关构建未被破坏。
7. **不改动 vendored**：`scintilla/`、`lexilla/`、`PowerEditor/src/`、`third_party/astyle/` 只读。

## 4. 模块 A —— 编码保存链路（两个静默错误）

**先写测试**（`tests/test_encoding.cpp`、`tests/test_editor_save.cpp`、`tests/test_main_window.cpp`）

1. UTF-8 透传、GBK 往返（`中文` ↔ `D6 D0 CE C4`）、BOM 规则、UTF-16 二进制判定（基线，防改坏）。
2. `iconv_open` 不支持的编码：`decode/encode` 都返回 `false` 且 sink 一次都不被调用。
3. `EditorView::saveCopyToFile()`：GBK 缓冲写出 GBK 字节；`UTF-8 BOM` 写出 BOM；原文档路径、脏标记、savepoint 全不变；转码失败不产生副本文件。
4. `saveToFile()` 转码失败：返回 `false`、原文件保持原内容、不 `SETSAVEPOINT`，`lastSaveError()` 含编码名。
5. `MainWindow` 保存失败发出可观测的 `saveFailed(path, reason)` 信号并给出模态提示（offscreen 下用 `QTimer` 自动关闭）。

**实现要点**
- `EncodingConverter`：`iconv_open` 失败即硬失败且不产出字节；`EILSEQ` 的 `?` / U+FFFD 替换属于已声明的有损转换，仍返回 `true`。
- `EditorView`：抽出 `writeEncodedFile()` 用 `QSaveFile` 事务写（BOM + 分块转码 + `commit()`，失败 `cancelWriting()`）；新增 `saveCopyToFile()`、`lastSaveError()`；`saveToFile()` 严格传播失败。
- `MainWindow::onSaveCopyAs()` 改调 `saveCopyToFile()`；四个保存入口统一 `reportSaveFailure()`；「全部保存」收集失败项汇总一次提示。
- 不触碰 v1.0.8 的格式化结果写回路径（`applyFormattedText` 只改内存，不走这里）。

**验收**：`ctest` 全绿；GBK 文件「拷贝另存为」用 `iconv` 校验；不支持编码时磁盘无脏数据。

# 追加章节：模块 F —— 打开文件夹（左侧目录树）

> 起始基线：上述模块 0~E 全部完成，8 个测试类 55 项全绿，主程序 Release LTO 构建通过。
> 前置评估：`docs/文件夹树技术评估.md`。结论：`npp-explorer-plugin` 不满足极致高性能且为 Win32-only，可移植代码 0 行。
> 需求方决策：**改用 Qt 原生 `QFileSystemModel + QTreeView + QDockWidget` 实现，不引入该插件任何代码。**

## 11. 需求与性能红线

用户在**文件菜单**或**工具栏**选择「打开文件夹」→ 选择本地目录 → APP **左侧展示目录树** → 点击树中文件在**主区域（现有标签页）**展示。

极致高性能红线（任一条不满足即视为失败）：

1. 打开文件夹只读根一层，**禁止递归预扫描**（禁止 O(N) 磁盘 IO 与 O(N) 常驻内存）。
2. 不自建扫描线程、不自建 watcher、不自建全量索引 —— 复用 `QFileSystemModel` 内建的惰性 `canFetchMore/fetchMore` 与 inotify watcher。
3. 图标按「目录 / 文件后缀」缓存，禁止逐文件 MIME 查询（对比插件的逐项 `SHGetFileInfo`）。
4. 不阻塞 UI 线程；不引入跨线程共享可变状态。
5. 不回退 v1.0.8 能力：代码格式化、拖拽打开、透明图标、既有 55 项测试与 `TestV108Baseline` 必须保持全绿。

## 12. 架构设计

**新增 `src/widgets/FolderTreePane.h/.cpp`**（`QDockWidget` 子类，与 `MainWindow` 解耦、可独立测试）：

| 接口 | 说明 |
|---|---|
| `bool setRootPath(const QString& path)` | 校验目录存在；`QFileSystemModel::setRootPath` + `QTreeView::setRootIndex`；失败返回 false 且**不改变当前根** |
| `QString rootPath() const` / `QModelIndex rootIndex() const` | 当前根，供测试断言 |
| `QFileSystemModel* model() const` / `QTreeView* view() const` | 惰性契约测试需要 |
| `void activateIndex(const QModelIndex&)` | public；把「点击」逻辑从鼠标事件里抽出来，测试可直接打 |
| `signals: void fileActivated(const QString& absolutePath)` | 仅文件触发，目录不触发 |

内部实现要点：
- `QTreeView` 隐藏 `Size/Type/Date Modified` 列（只留 Name），`setSortingEnabled(true)`，`setUniformRowHeights(true)`（大目录滚动优化），`setHeaderHidden(true)`。
- `QFileSystemModel::setRootPath()` 只建立根路径监视；子目录内容在用户展开时才 `fetchMore`。**不做任何 `QDirIterator` / 递归遍历**。
- 轻量 `FolderTreeIconProvider`：目录与文件各用一个 `QStyle` 标准图标，按后缀用 `QHash<QString,QIcon>` 缓存；零资源依赖、零逐文件 MIME 查询。Qt6 用 `QAbstractFileIconProvider`，Qt5 回退 `QFileIconProvider`，条件编译隔离。
- 单选、单击激活（`clicked` 与 `doubleClicked` 都连到 `activateIndex`），目录点击交给 `QTreeView` 自身展开/折叠，不触发 `fileActivated`。

**`MainWindow` 集成**：
- `setupFileMenu()` 增加「打开文件夹(&D)...」；`setupToolBar()` 增加同名动作（新增 `folder-tree` 图标，走 `tools/gen_toolbar_icons.py` 生成 dark/light × 16/32 PNG 与 qrc）。
- `setupViewMenu()` 增加 checkable「文件夹树(&T)」，与 dock 的 `visibilityChanged` 双向同步，用户关掉 dock 后能再打开。
- `QDockWidget* _folderDock`（`objectName = "folderTreeDock"`）在构造时 `addDockWidget(Qt::LeftDockWidgetArea, ...)`，**初始隐藏**；不影响现有 `setCentralWidget(_tabManager)` 与 `setMenuWidget(header)` 自绘标题栏。
- `onOpenFolder()` 弹 `QFileDialog::getExistingDirectory`；抽出 public `openFolderPath(const QString&)` 供测试绕过模态框。
- `fileActivated` → 复用 `MainWindow::openFile()`（自动带编码识别、语言、inotify 监控、近期文件）。
- 新增 QAction 自动被 `ShortcutManager::collectActions()` 收集，映射器无需改动。

**`ThemeManager`**：dark / light 两套 QSS 各补 `QDockWidget`、`QDockWidget::title`、`QTreeView`（背景、选中态、hover、边框、交替行色）规则；改样式必须两套都改（HANDOFF 已记录的陷阱）。

# 第 32 节：单实例 IPC 进程通信与文件打开延迟消除开发计划

## 32.1 需求背景与痛点诊断
1. **多进程割裂问题**：
   - 用户从文件管理器（如 Nautilus/GNOME Files）右键“用 Notepad++ 打开”文件时，目前会启动全新进程，造成窗口大量堆叠，且破坏了 Notepad++ 统一标签页编辑的核心体验与会话一致性；
2. **加载延迟与文件管理器缩影投影问题**：
   - 重复启动导致每个新文件打开都要经历完整的 Qt 运行时加载、96 种语言高亮规则与 93 套主题 XML 同步解析，耗时较长；
   - GNOME Shell 在接收到桌面启动序列未完成期间，会对触发它的文件管理器窗口应用等待投影与动画（“本地文件所在目录缩影”）；
   - `main.cpp` 中先 `window.show()` 再打开命令行传入的文件，导致首帧先画空白文档再切入文件内容，产生短暂视觉撕裂。

## 32.2 解决方案与技术架构
1. **基于 `QLocalServer` / `QLocalSocket` 的轻量极致高性能 IPC**：
   - 统一由 `SingleInstance` 模块管理（`src/utils/SingleInstance.h/cpp`）；
   - Socket 名称基于用户 UID 隔离（`notepad-plus-plus-linux-${UID}.sock`），权限安全；
   - 新启动进程在进入复杂耗时的配置载入前，先行尝试连接该 Socket：
     - 若已有实例运行：直接将要打开的文件绝对路径发送过去，完成桌面启动通知闭环，次级进程立即以 0 状态码秒级退出；
     - 若无实例运行（或检测到前次异常退出的残留僵尸 Socket）：清除死文件，转为主实例启动监听，并继续主程序生命周期；
   - 保留 `-multiInst` / `--multi-instance` 命令行参数支持，允许用户在有特殊需求时明确多开窗口。
2. **主窗口快速激活与延迟消除**：
   - 收到外部文件打开请求时：主实例循环调用 `openFile(path)`，立即切换至该标签；
   - 窗口激活：处理窗口最小化恢复（`showNormal`）、置前（`raise`）、获取输入焦点（`activateWindow`）；
   - 启动流程规整：首次冷启动传入文件时，先 `openFile` 装配完成再 `show()` 窗口，消除白屏/空标签闪烁。

# 追加章节：模块 J —— TypeScript / TSX 语法高亮修复

> 基线：模块 H / I 完成，14 个测试类全绿。用户报告 `.ts` 文件没有高亮，而语言菜单能识别 TypeScript。

## J.1 现象与根因

| 环节 | 探测结论 |
|---|---|
| 语言资源 | `PowerEditor/src/langs.model.xml:598` 有 `<Language name="typescript" ext="ts tsx">`，含 `instre1` / `type1` / `substyle1~8`；`ts` 在该文件中唯一归属 TypeScript |

| 扩展名识别 | `StyleManager::loadConfigs()` 建 `_extToLang["ts"]="typescript"`（`StyleManager.cpp:156`）；`loadFromFile()` → `detectLanguageByExt("ts")` → `applyLanguage("typescript")`，**这一步是好的** |
| 上游依据 | `PowerEditor/src/ScintillaComponent/ScintillaEditView.cpp:191` 明确登记 `{L"typescript", …, "cpp"}`；`setTypeScriptLexer()` 用 cpp lexer，并设 `lexer.cpp.track.preprocessor=0`、`lexer.cpp.backquoted.strings=1` |
| **断点** | `StyleManager::getLexerName()` 的 `s_lexerMap` 没有 `typescript`，未命中时直接 `return langName` → `CreateLexer("typescript")` 在 Lexilla 目录里找不到同名模块 → 返回 `nullptr` |

`lexilla/include/SciLexer.h` 没有 `SCLEX_TYPESCRIPT`，`lexilla/src/Lexilla.cxx` 目录也没有名为 `typescript` 的模块；另有一个语义不一致的兜底：`detectLanguageByExt()` 在 XML 未加载时把 `ts/tsx` 判成 `javascript`。

1. `StyleManager::getLexerName()` 增补 `{"typescript", "cpp"}`，与上游登记一致。

关键字槽位无需新增：`applyLanguage()` 的 `lexerName == "cpp"` 分支已把 TypeScript 的 `instre1` → slot 0、`type1` → slot 1，正好对应主题里的 5 / 16 号样式。

# 追加章节：模块 N —— HexView 复检与极致性能改造（对齐原始字节 + 视口惰性读取）

> 背景：模块 M（另一智能体实现）落地后复检，发现两处硬伤：
> (1) HexView dump 的是 Scintilla 解码后的 UTF-8 缓冲，并非磁盘原始字节（UTF-16/GBK/二进制会被改写、BOM 被剥离）；
> (2) 每次开启都同步整份 `documentBytes()` 拷贝 + 常驻整份内存，大文件卡顿，违反「极致高性能」红线。
> 本章节即针对上述两点的改造；模块 M 中「大文件与 NUL 字节流性能达标」的说法经复检不成立，以本章为准。

## N.1 目标

- **原始字节保真**：已保存文件直接读磁盘原始字节，未保存文档回退内存缓冲。
- **零整份拷贝**：文件用 `mmap` 映射，`paintEvent` 只对可见窗口调用一次区间读取，O(可见字节)。
- **大文件健壮**：地址宽度按文件大小 8/16 位自适应；行数用 qint64 计算并夹取到 int（QScrollBar 上限）。
- **绘制降本**：整行拼接后一次 `drawText`，消除逐字节 QString 分配与 drawText 调用。

## N.2 设计

- 数据源抽象：`Source{ None, Memory, Mapped, File }`；`enum` + `mmap` 指针 + `QFile` 回退。
- 新增 `bool setFile(const QString&)`（mmap 惰性）、保留 `setData(QByteArray)`（COW 共享，不深拷）。
- 新增 `QByteArray bytesInRange(offset,len) const` 与内部 `bytesInRange(offset,len,char*) const`；`selectedByte()`/`paintEvent` 统一走它。
- `formatAddress(qint64, int digits=8)` 支持 16 位；实例用 `_addrDigits` 按 `_dataSize > 0xFFFFFFFF` 选择。
- 析构 `munmap` 释放；`releaseSource()` 统一清理。
- `TabManager::toggleHexView`：优先 `setFile(path)`，失败或无路径回退 `setData(documentBytes())`。

## N.3 测试设计（先红后绿，`tests/test_hex_view.cpp`）

## N.4 完成情况

- HexView 改为 `mmap` 原始字节源 + 视口单次区间读取；`setData` 走 COW，文件路径走零拷贝映射。
- 绘制由「逐字节 2 次 drawText」改为「整行 2 次 drawText」，消除每帧数百次小分配。
- `rowCount`/偏移内部用 qint64，地址 >4GB 自适应 16 位。
- 新增 4 组测试全绿；全量回归 18 个测试类 0 失败；主程序 LTO 构建通过；lint 0 错误。

## N.5 三项体验/一致性完善（本轮续）

1. **二进制自动进入十六进制**：`MainWindow::openFile` 在加载成功后检查 `buffer()->isBinary()`（含 NUL 的非 UTF-16 文件），自动触发「以十六进制查看」，避免用户在文本视图里看乱码。`isBinary` 由此从死代码变成有效信号。
2. **主题色板接入**：新增 `ThemeManager::hexViewColors(bool)`（`HexViewColors` 结构体），HexView 不再硬编码颜色；`setDarkMode` 时整体换色，与 Obsidian 深/浅 token 对齐。
3. **焦点高亮按侧显示**：`_isFocusInHex` 现在真正驱动绘制——只高亮当前焦点所在的 HEX 或 ASCII 单元格，而非两侧同时高亮。

测试：新增 `binaryFileOpensInHexView`、`themeColorsFollowDarkMode` 两用例；`TestHexView` 12 用例全绿。

## N.6 光标/点击命中不准的根因修复（字体栅格漂移）

- **现象**：十六进制视图里点击某字节，高亮落在别的列，越往右越偏。
- **根因**：列坐标按 `c * charWidth`（`charWidth = 宽度('0')`）计算，但全局 QSS 的 `QWidget{font-family}` 会在 polish 时把 HexView（及其 viewport）换成**比例界面字体**；比例字体里空格宽度≠数字宽度，绘制出的字符串相对栅格逐列累积左移，命中随之漂移。已用测试复现：`'0'` 宽 8、空格宽 4。
- **修复**：HexView 持有 `_monoFont`，`updateLayout` 与 `paintEvent` 都用它测量/设置字体（`painter.setFont(_monoFont)`），并在控件级样式表钉死等宽字体；`changeEvent(FontChange)` 重算布局。绘制与栅格同源，彻底不受 QSS 影响。
- **测试**：`monospaceFontSurvivesGlobalStyleSheet`（设置比例界面字体后断言 `'0'==' '=='W'` 推进宽度），`TestHexView` 13 用例全绿。

# 追加章节：模块 M —— 极致高性能二进制数据查看（Hex Viewer）

> 基线：模块 L 完成，全量测试通过。本模块为产品引入工业级原生的二进制数据查看功能（Hex Viewer）。
> 参考项目：`/media/wtian/GithubProjects/NPP_HexEditor`（Win32 插件版已做深度性能与架构评估）。

## M.1 参考项目评估与自研技术选型

1. **参考项目评估结论**：
   - 参考插件 `NPP_HexEditor` 为 Win32 GDI / CommCtrl 强绑定代码，不可直接跨平台引入；
   - 其架构缺陷为：借壳 Scintilla 存储二进制数据，大文件与 NUL 字节流下 Scintilla 行管理与内存膨胀严重，且视口重绘时存在大量逐单元格 `SendMessage` 消息传递，性能不达标；
   - 但其人机交互布局标准（地址列、Hex 区域、ASCII Dump 字符区域、双向选中同步联动）具备良好参考价值。
2. **本产品自研极致高性能架构**：
   - **控件形态**：新建 `HexView`，直接继承 `QAbstractScrollArea` 纯自绘，零子部件开销；
   - **零拷贝与大文件支持（Zero-Copy）**：数据层直接基于 `QByteArray` 内存切片或 `QFile::map`（系统级 `mmap`），打开数十 MB 乃至 GB 级大文件瞬时完成，内存开销为 0；
   - **视口按需渲染（Viewport-Only Rendering）**：基于滚动条仅计算并读取当前可见行的 30~50 行（480~800 字节）；
   - **256 元素十六进制静态查表法（Hex Lookup Table）**：彻底摒弃慢速 `sprintf`，直接通过 `kHexTable[byte]` 内存直拷完成地址与 Hex 转换，微秒级准备好绘制数据；
   - **单次批处理绘制（Single-pass Paint）**：在 `paintEvent` 一次遍历绘制地址、Hex 与 ASCII 文本，完美适配浅色与深色主题；
   - **无缝切换集成**：菜单 `视图(&V)` -> `以十六进制查看(&H)`（快捷键 `Ctrl+Alt+H`）及工具栏按钮，支持在当前标签页中一键在 Scintilla 文本视图与 HexView 之间极速切换。

# 追加章节：模块 P.6 —— 比对功能复检与整改（对齐“极致高性能”）

> 复检模块 P 的实现后发现：报告承诺与代码不一致，且存在功能硬伤。本模块只做整改，不新增外部依赖。

## P.6.1 复检结论（问题）

1. **O(D²) 内存**：`computeDiff` 把每个 d 的完整 `v` 存入 `trace`，两侧差异多时内存按平方增长，可能 OOM；与“线性空间 Myers”承诺不符。
2. **功能破坏**：`CompareWidget` 把 TabManager 的编辑器 `addWidget` 抢进 splitter，关闭对比后仅 `setParent(nullptr)`，标签页内容被掏空且未恢复。
3. **行内差异投机**：仅计算公共前缀+后缀，一处行内多个改动会被合并成一个大区间，不是真正的字符级 diff。
4. **非零拷贝**：`currentTextUtf8()` 各拷贝整份文本。
5. **红黑树**：`applyDiffVisuals` 用 `std::map` 累积占位行，正是报告批评的反模式。
6. **无性能护栏**：无大文件上限；线程模型未落地。
7. **基准测试投机**：只造少量差异（D 很小），恰好绕开最坏情况，`<50ms` 不能证明极致性能。

## P.6.2 整改方案

- **Diff 引擎**：改为 **Histogram/Patience 锚点 + 有界 Myers**：
  - 先裁公共前后缀；对区间内“两侧唯一”的行做锚点（排序 + LIS），按锚点递归切分；
  - 无锚点的小区间用**有界 Myers**（`maxD`/`cells` 上限，内存有界）；
  - 无锚点的大区间退化为“整块替换”，但按位置两两配对为 `Modified` 并计算行内差异（结果仍是正确、可用的差异，且 O(N)）。
- **行内差异**：前缀/后缀裁剪后，对中段做**字符级有界 Myers**，输出多段 `CharRange`。
- **零拷贝**：新增 `EditorView::currentTextView()`（`SCI_GETRANGEPOINTER`），比对直接读 Scintilla 内部缓冲，不再整份拷贝。
- **CompareWidget**：去掉 `std::map`（改为有序 `std::vector`）；`applyDiffVisuals` 幂等；大文件上限。
- **MainWindow**：对比使用**新建的编辑器副本**，绝不 reparent TabManager 的页面；关闭时销毁副本，标签页保持完好。
- **测试**：新增“两份文档全不相同（无锚点）大规模”最坏用例、“插入一行（全锚点）”用例、多段行内差异用例、关闭对比后标签页/编辑器仍可用用例；替换原有的投机基准。

## P.6.3 验收

- 最坏情况 2 万行全不相同在预算内完成且内存有界；现有功能与全量回归全绿；主程序 LTO 构建通过。

- **gdb 复现**（真实 X11 APP + `xdotool` 发送 `Ctrl+Alt+C`）：`SIGSEGV` 调用栈
  `QTabBar::count()` ← `MainWindow::syncBackups()` ← `QTimer::timeout`。备份定时器默认 **7 秒**，正好解释「约 10 秒」。
- **根因**：`MainWindow::createCompareView()` 直接调用 `setCentralWidget(_compareWidget)`，Qt 会把旧的 central widget（`_tabManager`）排队 `deleteLater()`。`onCloseCompare()` 里那句「脱离主窗口布局所有权，避免 setCentralWidget 误删」的注释说明早已知晓此坑，但**只保护了退出路径**。定时器随后访问悬空 `_tabManager` → `QTabWidget::count()` → 已删除的 `QTabBar` → 崩溃。
- **修复**：
  1. 新增 `MainWindow::switchCentralWidget()`：先 `takeCentralWidget()` 取回旧控件所有权（`hide()` + `setParent(nullptr)`）再 `setCentralWidget(next)`，进入/退出比对统一走它，两个视图都长期存活。
  2. `QPointer<TabManager> _tabManagerAlive` 哨兵 + `syncBackups()` 开头检查：即使将来任何原因导致对象被销毁，也只跳过本轮备份而非崩溃。
  3. 保留 `centralWidget()` 语义不变，既有集成测试无需调整。
- **测试**：新增 `compareModeKeepsTabManagerAlive`（`QPointer` 守卫 + 派发 `DeferredDelete` + 显式 `invokeMethod("syncBackups")`），**修复前红灯**（`guard.isNull()==true`）、修复后绿灯；另补 `compareViewStableAcrossEventLoop`、`repeatedRefreshWhileAsyncIsSafe`、`asyncCompareCloseDuringComputationIsSafe` 三个生命周期用例。
- **验收**：全量 CTest 100%；真实 APP + gdb 进入比对后存活 26 秒（跨多个备份周期）无 SIGSEGV，内核无新增 segfault；`noda` LTO 构建通过。
