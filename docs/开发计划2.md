## 2. 设计原则

1. **TDD**：每模块先写测试并跑出红灯，再写实现跑到绿灯；绿灯前不进入下一模块。
2. **不静默**：任何降级都必须有一条用户可见、带原因与后果的提示，以及一条可断言的程序状态。
3. **不丢数据**：保存失败绝不 `SETSAVEPOINT`、绝不清脏标记、绝不留下半成品文件（事务写）。
4. **单一事实来源**：快捷键表从真实 `QAction` 收集，自动包含 v1.0.8 的「代码格式化」，不再维护第二份清单。
5. **可测性优先**：序列化、路径探测、冲突检测等纯逻辑从 QWidget 抽出，测试同时打纯逻辑与 offscreen UI 绑定。
6. **不回退 v1.0.8 功能**：所有改造都要在测试中验证格式化、拖放、图标相关构建未被破坏。
7. **不改动 vendored**：`scintilla/`、`lexilla/`、`PowerEditor/src/`、`third_party/astyle/` 只读。

## 4. 模块 A —— 编码保存链路（两个静默错误）

**先写测试**（`tests/test_encoding.cpp`、`tests/test_editor_save.cpp`、`tests/test_main_window.cpp`）

1. UTF-8 透传、GBK 往返（`中文` ↔ `D6 D0 CE C4`）、BOM 规则、UTF-16 二进制判定（基线，防改坏）。
2. `iconv_open` 不支持的编码：`decode/encode` 都返回 `false` 且 sink 一次都不被调用。
3. `EditorView::saveCopyToFile()`：GBK 缓冲写出 GBK 字节；`UTF-8 BOM` 写出 BOM；原文档路径、脏标记、savepoint 全不变；转码失败不产生副本文件。
4. `saveToFile()` 转码失败：返回 `false`、原文件保持原内容、不 `SETSAVEPOINT`，`lastSaveError()` 含编码名。
5. `MainWindow` 保存失败发出可观测的 `saveFailed(path, reason)` 信号并给出模态提示（offscreen 下用 `QTimer` 自动关闭）。

**实现要点**
- `EncodingConverter`：`iconv_open` 失败即硬失败且不产出字节；`EILSEQ` 的 `?` / U+FFFD 替换属于已声明的有损转换，仍返回 `true`。
- `EditorView`：抽出 `writeEncodedFile()` 用 `QSaveFile` 事务写（BOM + 分块转码 + `commit()`，失败 `cancelWriting()`）；新增 `saveCopyToFile()`、`lastSaveError()`；`saveToFile()` 严格传播失败。
- `MainWindow::onSaveCopyAs()` 改调 `saveCopyToFile()`；四个保存入口统一 `reportSaveFailure()`；「全部保存」收集失败项汇总一次提示。
- 不触碰 v1.0.8 的格式化结果写回路径（`applyFormattedText` 只改内存，不走这里）。

**验收**：`ctest` 全绿；GBK 文件「拷贝另存为」用 `iconv` 校验；不支持编码时磁盘无脏数据。

# 追加章节：模块 F —— 打开文件夹（左侧目录树）

> 起始基线：上述模块 0~E 全部完成，8 个测试类 55 项全绿，主程序 Release LTO 构建通过。
> 前置评估：`docs/文件夹树技术评估.md`。结论：`npp-explorer-plugin` 不满足极致高性能且为 Win32-only，可移植代码 0 行。
> 需求方决策：**改用 Qt 原生 `QFileSystemModel + QTreeView + QDockWidget` 实现，不引入该插件任何代码。**

## 11. 需求与性能红线

用户在**文件菜单**或**工具栏**选择「打开文件夹」→ 选择本地目录 → APP **左侧展示目录树** → 点击树中文件在**主区域（现有标签页）**展示。

极致高性能红线（任一条不满足即视为失败）：

1. 打开文件夹只读根一层，**禁止递归预扫描**（禁止 O(N) 磁盘 IO 与 O(N) 常驻内存）。
2. 不自建扫描线程、不自建 watcher、不自建全量索引 —— 复用 `QFileSystemModel` 内建的惰性 `canFetchMore/fetchMore` 与 inotify watcher。
3. 图标按「目录 / 文件后缀」缓存，禁止逐文件 MIME 查询（对比插件的逐项 `SHGetFileInfo`）。
4. 不阻塞 UI 线程；不引入跨线程共享可变状态。
5. 不回退 v1.0.8 能力：代码格式化、拖拽打开、透明图标、既有 55 项测试与 `TestV108Baseline` 必须保持全绿。

## 12. 架构设计

**新增 `src/widgets/FolderTreePane.h/.cpp`**（`QDockWidget` 子类，与 `MainWindow` 解耦、可独立测试）：

| 接口 | 说明 |
|---|---|
| `bool setRootPath(const QString& path)` | 校验目录存在；`QFileSystemModel::setRootPath` + `QTreeView::setRootIndex`；失败返回 false 且**不改变当前根** |
| `QString rootPath() const` / `QModelIndex rootIndex() const` | 当前根，供测试断言 |
| `QFileSystemModel* model() const` / `QTreeView* view() const` | 惰性契约测试需要 |
| `void activateIndex(const QModelIndex&)` | public；把「点击」逻辑从鼠标事件里抽出来，测试可直接打 |
| `signals: void fileActivated(const QString& absolutePath)` | 仅文件触发，目录不触发 |

内部实现要点：
- `QTreeView` 隐藏 `Size/Type/Date Modified` 列（只留 Name），`setSortingEnabled(true)`，`setUniformRowHeights(true)`（大目录滚动优化），`setHeaderHidden(true)`。
- `QFileSystemModel::setRootPath()` 只建立根路径监视；子目录内容在用户展开时才 `fetchMore`。**不做任何 `QDirIterator` / 递归遍历**。
- 轻量 `FolderTreeIconProvider`：目录与文件各用一个 `QStyle` 标准图标，按后缀用 `QHash<QString,QIcon>` 缓存；零资源依赖、零逐文件 MIME 查询。Qt6 用 `QAbstractFileIconProvider`，Qt5 回退 `QFileIconProvider`，条件编译隔离。
- 单选、单击激活（`clicked` 与 `doubleClicked` 都连到 `activateIndex`），目录点击交给 `QTreeView` 自身展开/折叠，不触发 `fileActivated`。

**`MainWindow` 集成**：
- `setupFileMenu()` 增加「打开文件夹(&D)...」；`setupToolBar()` 增加同名动作（新增 `folder-tree` 图标，走 `tools/gen_toolbar_icons.py` 生成 dark/light × 16/32 PNG 与 qrc）。
- `setupViewMenu()` 增加 checkable「文件夹树(&T)」，与 dock 的 `visibilityChanged` 双向同步，用户关掉 dock 后能再打开。
- `QDockWidget* _folderDock`（`objectName = "folderTreeDock"`）在构造时 `addDockWidget(Qt::LeftDockWidgetArea, ...)`，**初始隐藏**；不影响现有 `setCentralWidget(_tabManager)` 与 `setMenuWidget(header)` 自绘标题栏。
- `onOpenFolder()` 弹 `QFileDialog::getExistingDirectory`；抽出 public `openFolderPath(const QString&)` 供测试绕过模态框。
- `fileActivated` → 复用 `MainWindow::openFile()`（自动带编码识别、语言、inotify 监控、近期文件）。
- 新增 QAction 自动被 `ShortcutManager::collectActions()` 收集，映射器无需改动。

**`ThemeManager`**：dark / light 两套 QSS 各补 `QDockWidget`、`QDockWidget::title`、`QTreeView`（背景、选中态、hover、边框、交替行色）规则；改样式必须两套都改（HANDOFF 已记录的陷阱）。

# 第 32 节：单实例 IPC 进程通信与文件打开延迟消除开发计划

## 32.1 需求背景与痛点诊断
1. **多进程割裂问题**：
   - 用户从文件管理器（如 Nautilus/GNOME Files）右键“用 Notepad++ 打开”文件时，目前会启动全新进程，造成窗口大量堆叠，且破坏了 Notepad++ 统一标签页编辑的核心体验与会话一致性；
2. **加载延迟与文件管理器缩影投影问题**：
   - 重复启动导致每个新文件打开都要经历完整的 Qt 运行时加载、96 种语言高亮规则与 93 套主题 XML 同步解析，耗时较长；
   - GNOME Shell 在接收到桌面启动序列未完成期间，会对触发它的文件管理器窗口应用等待投影与动画（“本地文件所在目录缩影”）；
   - `main.cpp` 中先 `window.show()` 再打开命令行传入的文件，导致首帧先画空白文档再切入文件内容，产生短暂视觉撕裂。

## 32.2 解决方案与技术架构
1. **基于 `QLocalServer` / `QLocalSocket` 的轻量极致高性能 IPC**：
   - 统一由 `SingleInstance` 模块管理（`src/utils/SingleInstance.h/cpp`）；
   - Socket 名称基于用户 UID 隔离（`notepad-plus-plus-linux-${UID}.sock`），权限安全；
   - 新启动进程在进入复杂耗时的配置载入前，先行尝试连接该 Socket：
     - 若已有实例运行：直接将要打开的文件绝对路径发送过去，完成桌面启动通知闭环，次级进程立即以 0 状态码秒级退出；
     - 若无实例运行（或检测到前次异常退出的残留僵尸 Socket）：清除死文件，转为主实例启动监听，并继续主程序生命周期；
   - 保留 `-multiInst` / `--multi-instance` 命令行参数支持，允许用户在有特殊需求时明确多开窗口。
2. **主窗口快速激活与延迟消除**：
   - 收到外部文件打开请求时：主实例循环调用 `openFile(path)`，立即切换至该标签；
   - 窗口激活：处理窗口最小化恢复（`showNormal`）、置前（`raise`）、获取输入焦点（`activateWindow`）；
   - 启动流程规整：首次冷启动传入文件时，先 `openFile` 装配完成再 `show()` 窗口，消除白屏/空标签闪烁。
